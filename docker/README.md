# Local Docker environment (ARBICOP)

Support files for the compose stacks at the project root. Current state only; the old chronological changelog is in
`D:/TRABAJO/RESPALDOS/arbicop/limpieza-2026-11-23/docker/README.md`.

## Stacks and ports

| Compose file | Purpose | Ports | Start |
|---|---|---|---|
| `docker-compose.yml` (project `web-arbicop`) | Reference WordPress: root site at `/` + shop (WooCommerce) at `/tienda`, one Apache container, MariaDB, optional phpMyAdmin/wp-cli (`--profile tools`) | WP 8082, DB 3308 (`wp`/`wp`, root/root), phpMyAdmin 8083 | `docker compose -p web-arbicop up -d db wordpress` |
| `docker-compose.static.yml` | Production-like Apache serving `dist/` (honours `.htaccess`) | 8084 | `docker compose -f docker-compose.static.yml -p arbicop-static up -d --build` |
| `docker-compose.libro-test.yml` | Libro de Reclamaciones e2e on real PHP (8.4, 8.1, strict limits, failure injection) | 8085, 8086, 8087, 8088 | `docker compose -f docker-compose.libro-test.yml -p arbicop-libro up -d --build`, then `node tools/libro-e2e.mjs --fresh` |
| `docker-compose.deploy-test.yml` | cPanel deploy + cutover + rollback simulation (fake data only) | 8090 (stale), 8092 (clean) | `docker compose -f docker-compose.deploy-test.yml -p arbicop-deploytest up -d --build`, then `bash docker/deploy-test/run.sh` |

Stop any of them with `docker compose -p <project> down` (`-v` also drops its volumes).

## How the local WordPress works

- WordPress files and databases live in the named volumes `web-arbicop_wpfiles` and `web-arbicop_dbdata`, NOT in the project folder.
  The project folder no longer contains any WordPress core, plugins, themes or uploads.
- Bind-mounted from here (read by compose): `docker/wp-config.root.php`, `docker/wp-config.tienda.php`, `docker/local.ini` (PHP limits),
  `docker/initdb/01-dbs.sql` (creates `arbicopc_504` prefix `wpfb_` = root site and `arbicopc_wp847` prefix `wp1k_` = shop on first DB init).
- `docker/wp-config.*.php` are GENERATED, git-ignored and contain production salts. Regenerate with
  `python docker/gen-configs.py <SOURCE_DIR>` where `SOURCE_DIR` holds `wp-config.php` and `tienda/wp-config.php`
  (the production configs; DB host becomes `db`, URLs local, cron off). Copies are in `D:/TRABAJO/RESPALDOS/arbicop/wp-configs/{root,tienda}/wp-config.php`
  (rename the layout accordingly) or inside `arbicop.zip`.
- To rebuild the local WordPress from scratch (only if the volumes are lost): extract WordPress files from
  `D:/TRABAJO/RESPALDOS/arbicop/arbicop.zip`, import `arbicopc_504.sql` and `arbicopc_wp847.sql` (same folder) into the two databases, then search-replace
  `https://arbicop.com` with `http://localhost:8082`. The zip, dumps and `MANIFEST.md` (sha256) are the only copy of the legacy sites outside production.
- wp-cli: `MSYS_NO_PATHCONV=1 docker compose -p web-arbicop --profile tools run --rm -T wpcli --path=/var/www/html[/tienda] <cmd>`.
- The static site no longer depends on this WordPress: `src/` is the source of truth (see the root `README.md`).

## Shop chrome (current)

The local shop renders the header/footer from `tienda/wp-content/mu-plugins/arbicop-chrome*` (generated by `npm run build`). To try it locally copy the mu-plugin files into the `web-arbicop_wpfiles` volume (`docker cp tienda/wp-content/mu-plugins/arbicop-chrome web-arbicop-wordpress-1:/var/www/html/tienda/wp-content/mu-plugins/`, same for `arbicop-chrome.php` and `arbicop-shop-cart.php`, then `docker exec web-arbicop-wordpress-1 apachectl -k graceful`) and copy `dist/assets` to `/var/www/html/assets` (production serves it from the docroot). The local shop DB was restored to the production content of templates #20/#23 before the first test; no DB writes are needed. Backup of the pre-test local state: `D:/TRABAJO/RESPALDOS/arbicop/limpieza-2026-11-23/docker/backups/shop-local-before-chrome/`.
